# 让 agent 审查"这次会话改了什么"：三种提示词写法

> 核对时间：2026-11-05。命令归属见同目录 `三种审查命令的分工.md`；本篇只讲**怎么开口**，不重复命令来源。
> 结论基于会话实践，**未做 A/B 量化对比**；机制部分（diff 是事实源、上下文会压缩）属已验证的一般行为。

## 一句话

不要指望 agent"记得"自己改了什么——**让它跑 `git diff`**。会话记忆会被压缩、丢细节、甚至记错；工作区 diff 是唯一可信的事实源。

## 1. 三种写法

### 写法 A：直接要求（最省事，最不可靠）

> 请基于当前 Session 中你做过的所有更改，做一次代码审查。

问题：agent 只能靠对话记忆重建改动。长会话里前面几轮已被压缩成摘要，"改了哪几行、为什么改"经常复原不出来。

### 写法 B：强制读 diff（推荐）

> 运行 `git diff` 和 `git status --short`，查看当前工作区所有未提交改动。对这部分 diff 做严格 Code Review，关注逻辑错误、安全、性能、可读性。以 PR 评论格式输出：每条给 `文件:行`、严重度（blocker / major / minor / nit）、问题、修改建议。不要修改代码。

优点：改动范围由 git 决定，不依赖记忆；`git status` 能发现**未跟踪的新文件**（`git diff` 看不到它们）。

### 写法 C：角色切换 + 只读约束（最严格）

> 通过 `git status` 与 `git diff` 确认本次修改涉及的文件，切换为 Reviewer 角色：只读、不改代码、不执行写操作。输出一份审查报告，先判断"改动是否达成原任务目标"，再按 blocker / major / minor / nit 分级列问题，每条指到文件与行。

适合要求"审查者不能顺手把问题改掉"的场景——一旦允许改，审查就从"发现问题"变成"边审边修"，原始问题会被掩盖。

## 2. 必加的四个约束

| 约束 | 为什么 | 怎么写 |
|---|---|---|
| **只读** | 防止审查者顺手改代码，掩盖问题 | "不要修改任何文件；只输出报告" |
| **范围** | 防止它把整个仓库都审一遍 | "只审 `git diff` 覆盖的改动，未改动文件不评价" |
| **降噪** | 防止满屏格式意见 | "不评论纯格式/命名偏好；只报会影响正确性、安全性、性能、可维护性的问题" |
| **格式** | 便于逐条处理 | "每条：文件:行 / 严重度 / 问题 / 建议；同文件多条合并" |

## 3. 分阶段审查（大改动）

一次 diff 太大时，模型会"扫读"并漏掉中段。拆成两轮：

1. **意图轮**：先只回答"这组改动想解决什么、有没有跑偏、有没有该改没改的"。
2. **实现轮**：再逐文件看正确性与边界条件。

比一次性丢整个 diff 更稳，尤其是改动跨十几个文件时。

## 4. 与内置命令怎么配合

- 要**引擎级、独立子会话**的审查：用 `/review`（跑在子会话里，不污染当前上下文）。
- 要**宿主判断"这次改动对不对、够不够"**：用 `/workspace-review`。
- 要**交接给另一个会话再审**：用 `/handoff-review`。

三者区别见 `三种审查命令的分工.md`。本篇的提示词适合**没有这些命令、或想自定义审查维度**的场合。

## 5. 常见失败模式

- **只跑 `git diff`**：漏掉未跟踪的新文件。必须同时 `git status --short`。
- **审查者拿到的是旧 diff**：agent 在审查过程中又改了文件。所以先要求它"只读"，或在审查前 `git stash` 冻结工作区（**有风险，先确认没有未保存的重要改动**）。
- **审查范围包含生成物**：`dist/`、`node_modules/`、lock 文件会把 diff 撑爆。提示词里明确排除，或用 `git diff -- . ':(exclude)dist'`。
- **只报问题不给位置**：无法落地。强制 `文件:行`。
