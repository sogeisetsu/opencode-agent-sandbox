# 分支删除：什么时候会真的丢东西

## 先分清两件事

- 删**分支** = 删一个指向 commit 的指针，commit 本身还在（只要还有别的引用）。
- 删**工作树** = 删工作目录里的文件，**未提交的内容直接没了**。

删分支前必须问一句：**这些分支上有没有 main 没有的 commit？**

> 草图：[`删分支会丢什么-提交图.excalidraw`](./删分支会丢什么-提交图.excalidraw)（OpenChamber 的 Files 视图里点开就是画布）

- `featA` 上有 3 个 main 没有的提交 → 删分支后成孤儿，没推过就只剩 reflog 兜底。
- `featB` 与 main 同一点 → 删掉不丢任何提交。

## 三个只读检查

```bash
git branch -vv                 # 每个分支的指向 + 上游 + 最后一条提交
git branch --merged main       # 已并入 main 的（通常可安全删）
git log --oneline main..<branch>   # 该分支独有的提交，输出为空 = 没有独有提交
```

## 删除

```bash
git branch -d <branch>   # 安全模式：未并入当前分支会拒绝
git branch -D <branch>   # 强制：未并入也删，独有提交变孤儿
```

`-D` 之后 commit 不会立刻消失，还会被 reflog / `git fsck --lost-found` 捞回来一段时间——但这是**临时**兜底（reflog 会过期、会被清理）。

真正决定"能不能捞回来"的是**有没有推送过**：

- 已推到 remote → 本机删干净也能从远程 `fetch` 回来。
- 没推过（或根本没有 remote）→ 只有 reflog 这一层薄保护，过一阵就真没了。

## 删远程分支

本地分支和远程分支是**两个独立的指针**，本地 `branch -d` **不会**动远端：

```bash
git ls-remote --heads origin <branch>          # 远端那个 ref 指向哪个 sha
git merge-base --is-ancestor <branch> main \
  && echo ANCESTOR_OK                          # 退出码 0 = 无独有提交
git push origin --delete <branch>              # 再删远端
```

- 前置检查的关键是**sha 对得上**：`ls-remote` 出来的 sha 与本地分支一致、且该 sha 已在 main 上，删远程就不丢任何提交（实测）。
- `push origin --delete` 成功时输出形如 `- [deleted] <branch>`，退出码 0。
- 删远程是**对所有人可见**的操作（public 仓库尤其），比删本地分支的风险高一档：先确认没有别人的分支/PR 挂在上面。
- 只删本地不删远程 = 下次 `fetch` 会把 `remotes/origin/<branch>` 又拉回来，看着像"没删干净"。

## 已确认的边界

- 所有分支都与 `main` 同 commit 时，`-D` 全部删干净**不丢任何提交**（实测）。
- 无 remote 时：删分支/工作树/未提交改动**没有远端兜底**，属于不可逆操作，动手前先确认。
- 有 remote 时：**未推送过的分支仍然不可恢复**，"有远端"不代表安全。

## 一句话检查清单

1. `git status` 干净吗？
2. `git branch --merged` 覆盖了要删的分支吗？
3. 每个要删的工作树，`git -C <path> status --porcelain` 是空的吗？
4. 有没有 remote？远端有没有这些分支？
5. 删本地分支后，远端还有没有同名 ref？要一起删就 `push origin --delete`。
6. 以上都确认了，再 `-D` / `remove --force`。
