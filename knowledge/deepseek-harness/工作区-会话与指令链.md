# DSH 工作区、会话与指令链

> 核对：2026-11-12。依据：2026-11-09～11-11 的 13 个会话日志复盘；工作区注册表、目录存在性等静态事实本轮实读复核。DSH 为 nightly 预发布，路径常量与行为会漂移。

## 默认工作区：不是设置项，是「首启登记的第一条记录」

- 目录由代码常量 `DEFAULT_WORKSPACE_DIRECTORY` 写死为 `<系统文档目录>\deepseek-harness\default-workspace`，**不跟随界面语言**。系统「文档」目录被 OneDrive 重定向时，实际路径随之变化（**已验证**：本机就是重定向后的位置）。
- 登记状态在 `~/.dsh/storages/workspace.json`：`global.defaultWorkspaceId` 指向 `tables.workspaces` 里的一条记录，`title` 为 `default-workspace`（**已验证**）。
- 它有三个性质：可**重命名**（只改标题）、可**删除**（只从列表移除，文件夹和会话都保留，会话落到「未分组」）、**删除后不会自动重建**（首次初始化只做一次）。

改法（从推荐到不推荐）：

| 方案 | 做法 | 限制 |
|---|---|---|
| ① 换一个目录来用 | 侧边栏「添加工作区…」→ 选任意已存在绝对路径；新建会话时选它 | 纯界面操作，无副作用 |
| ② 改自动创建位置 | patch 加 `workspace-controller` 的 `documentsDirectory` / `documentsLookupTimeoutMs` | **只在「注册表为空且没有任何会话」时运行**；已有数据时加它不会迁移 |
| ③ 直接改注册表 | 退出应用后改 `tables.workspaces.<id>.path` | 应用管理的状态文件，运行中改写易不一致；不推荐 |

**连带影响**：会话 cwd = 工作区路径，而 `workspace-write` 沙箱范围跟着 cwd 走——换工作区等于换可写范围。

## 「未分组」不是工作区，是兜底分组

侧栏只按一个条件分组：**会话 cwd 是否等于某个已登记工作区的路径**。对不上的（以及工作区被删后遗留的）全部落进「未分组」。

- 它在 `workspace.json` 里**没有记录**，所以没有重命名/删除菜单，也不会因为里面出现会话就自动变成工作区。
- DSH **只在首次初始化**时按历史会话补建工作区，之后不再按 cwd 自动新建 → 这些会话会一直挂着，除非归档或手动删。
- 典型来源：一次性连通性测试（cwd 不在任何已登记目录）。这类会话会保留并显示「未分组」，属于预期行为。

## 三种「消失」的语义差别（选错会丢数据）

| 操作 | 入口 | 磁盘上发生了什么 | 可恢复性 |
|---|---|---|---|
| 归档会话 | 右键 / `…` 菜单 / 行尾盒子图标 | 会话文件保留，加归档标记；默认视图隐藏 | ✅ 可取消归档（视图选项 → 全部对话） |
| 删除工作区 | 右键工作区 → 删除工作区 | 只从 `workspace.json` 移除；**文件夹与会话都保留** | ✅ 会话仍出现在「未分组」 |
| 手动删会话 | 退出 DSH 后删目录 | 文件与投影缓存真的消失 | ❌ 无回收站 |

**DSH 本体没有「删除会话」这个能力，是设计**：侧栏文档「已知限制」原文 *"没有 Session 删除：会话可以归档但绝不会被删除"*；会话持久层写明「不删除会话文件…… seam 无删除接口」。要删只能：①装社区插件（见[插件体系与安装](插件体系与安装.md)）；②退出后手动删磁盘：

```text
~/.dsh/sessions/<编码后的工作区路径>/session-<id>/
~/.dsh/storages/session_projcache/sessions/session-<id>.json
```

（只需这两个地方；若该会话在 `workspace.json` 里，还要从 `tables.workspaces.<id>.sessionIds` 与 `archivedSessionIds` 里摘掉。）

> ⚠️ 手动删是**不可逆**的：先退出 DSH（含托盘），先确认路径确实是目标 session 目录，再执行删除；不要对通配符路径操作。

## 会话文件格式与「考古」方法

| 文件 | 内容 | 用途 |
|---|---|---|
| `~/.dsh/sessions/<slug>/session-<id>/session.v4.jsonl.zstd` | 原始事件流水（JSONL，**zstd 压缩、多帧追加**） | 取任何事件级证据：模型请求、工具调用、标题请求、权限变更 |
| `~/.dsh/storages/session_projcache/sessions/session-<id>.json` | 投影缓存（`record.rows.*`） | 取当前状态：`title.val`、`sessionStats`、`contextPressure`、`modelSelection` |
| `~/.dsh/storages/workspace.json` | 工作区→会话索引 | 找会话属于哪个工作区 |

### 坑：zstd 是多帧的

`zlib.zstdDecompressSync(buf)` 只解出第一帧（往往只有会话头一行）。必须按 magic `28 b5 2f fd` 逐帧切分再解：读帧头 → 解析 FHD/窗口描述符/字典 ID/FCS → 逐块读 3 字节块头直到 last 块 → 跳过可选 4 字节校验和 → 下一帧（**已验证**：会话内用自写切帧器解出了完整事件流）。

事件类型很有用：`user/message`、`assistant/message`、`tool/call`、`tool/result`、`turn/start`、`session/title-llm-request`、`permission/preset`、`sandbox/mode`、`model/selection`、`compaction/summary`。主题阅读时只取 user/assistant 文本 + 工具调用参数，就能还原一场会话。

## 会话搜索：两个实例、两套访问策略

同一个 SQLite 后端（`dsh-session-query-sqlite`）在进程里有**两个互相隔离的实例**：

| 维度 | 宿主实例 `session-query-sqlite` | 组内实例 `optional-session-query-sqlite` |
|---|---|---|
| 谁定义 | 基础层 `openAt: never`，被侧栏搜索插件的 bundle patch 改成 `path: ':memory:'` + `openAt: first-search` | `dsh-experimental-session-search` 自己的 patch（`isolate: sessionQuery: true` 的 group 里） |
| 消费者 | **用户**：GUI 侧栏搜索、`/resume` 类检索（`sessionController.search`） | **模型**：5 个只读工具 |
| 能否跨工作区 | ✅ 能：只按「可见会话」过滤，不校验 cwd | ❌ 不能：`workspace-access.ts` 要求目标会话 cwd 与调用方**字符串严格相等** |
| 索引 | 内存（`:memory:`），重启重建 | 内存，重启或重开 bundle 重建 |
| 报错信号 | 宿主那份若关着，侧栏报 `Search failed: … SESSION_QUERY_SEARCH_DISABLED` | 越界时返回 `Error: session target is outside the caller workspace` |

一句话：**「能不能全都搜」不是数据库能力问题，而是「谁调用、调用前怎么过滤」的问题**。后端文档自己写明「无调用方授权，这是可信服务，访问策略由模型工具或 UI 自己执行」。

模型侧的 5 个工具（`@deepseek-ai/dsh-experimental-session-search`）：`session_search`、`session_event_search`、`session_trace`、`session_event_trace`、`session_event_read`。可调参数只有 `maxSearchResults`（默认 100）与 `searchTimeoutMs`（默认 30000）——**没有任何开关能解除工作区限制**。

想让宿主索引跨重启保留（锦上添花）：在 profile patch 末尾加

```yaml
- id: session-query-sqlite
  config:
    path: '<DSH_HOME>/cache/session-search.db'
    openAt: first-search
```

两个字段都要写（整段替换语义）；不加也只是一次性重建索引。

## 全局指令：`AGENTS.md` 的解析链

DSH 有全局 `AGENTS.md`，而且有**两个**全局根：

| 层级 | 位置 | 说明 |
|---|---|---|
| 用户全局① | `~/.dsh/AGENTS.md` | = `$DSH_HOME/AGENTS.md`，harness home |
| 用户全局② | `~/.agents/AGENTS.md` | = `$DSH_AGENTS_HOME`（缺省 `~/.agents`），跨工具共享根 |
| 项目链 | 从项目根（`.git` 为标记）逐层到 cwd，每层 `AGENTS.md`、`CLAUDE.md` | 越深优先级越高 |
| 本地叠加 | 同层 `AGENTS.local.md`、`CLAUDE.local.md` | 仅项目层有；两个全局根没有 overlay |

机制要点（`@deepseek-ai/dsh-agent-instructions` 文档 + 会话实测）：

- **注入形态**：每条链在会话第一次请求时合成一条**持久的 `user` 角色消息**，用 `<system-reminder>` 包裹（内含 `Instructions from: …` 分段），作为普通历史参与回放/压缩/恢复；**不写进 system prompt**，也不覆盖系统、开发者或用户直接指令。
- **预算**：每条链 `maxBytes` 默认 65536 字节，两条链分别算。超预算先整份丢弃较宽泛的文件，最后才截断最具体的文件，并输出 `Workspace instruction budget ...` 提示。
- **刷新不是 watcher**：靠 `read`/`write`/`edit` 触达更深目录后在下次请求补入；内容变化则替换、消失则发移除通知；会话恢复会对账基线；切换工作目录会重载项目链。**shell 里 `cd` 不算**。
- **去重**：同组内去空白后内容一致的文件只渲染一次（`CLAUDE.md` 复制 `AGENTS.md` 不会双倍占 token）。
- **空链不产生内容**：两个全局根都不存在时，会话不会载入任何指令；想启用直接新建 Markdown 即可，**不需要改任何配置**，新开会话或恢复后生效（本机 2026-11-12 实读：两者均不存在）。

容易混淆但不等价的东西：`cordis.patch.yml` 改的是**行为**；`~/.agents/skills` 是按需加载的**能力**；`~/.dsh/sessions` 是**过往记录**而不是自动记忆。DSH 没有「自动写记忆文件」的机制，长期偏好的正式位置就是上面两个全局 `AGENTS.md`。

## 会话标题插件：一个「静默失败」的典型案例

- bundle：`@deepseek-ai/dsh-experimental-session-titles-bundle`；干活的组件：`@deepseek-ai/dsh-session-title-all-prompts-llm`（patch 条目 id `optional-session-title-all-prompts`）。
- 行为：**每发一条新用户消息修订一次**；不在一轮中实时更新；不追溯旧会话；标题一旦生成，模型被要求「除非主要任务实质变化否则原样保留」；手动重命名过的标题会被「钉住」。
- 默认配置：`maxOutputTokens: 64`。**推理型模型会把 64 token 全花在 `reasoning_content` 上**，标题输出为 `null`，插件只记一条日志警告（`title output reached maxOutputTokens`）→ 保留旧标题，UI 无提示 → 看起来像「从没生效」。
- 证据：全量统计两条推理模型路由的标题请求成功率均为 **0**；对照实验 `max_tokens=64` → `finish_reason: length`、`content: null`，`max_tokens=256` → 正常出标题（**已验证**）。

修复（字段语义可复用；下列数值是本机当前值，不是通用推荐）：

```yaml
- id: optional-session-title-all-prompts
  name: "@deepseek-ai/dsh-session-title-all-prompts-llm"
  config:
    targetWords: 5
    targetCjkCharacters: 10
    maxInputBytes: 4096
    maxOutputTokens: 1024     # 默认 64 不够推理模型用
    timeoutMs: 120000
    provider: <route-id>      # 也可固定到非推理模型
    model: <model-id>
```

验证方式：改完随便发一条消息，然后从会话日志里取 `session/title-llm-request` 事件的 `maxTokens`，再看 `projcache` 的 `record.rows.title.val` 是否被成功提交。注意**「请求成功」与「标题文字变化」是两件事**——模型可能判定原标题仍准确而原样保留。

判断「插件是没加载，还是加载了但静默失败」的顺序：①`package.json` 的 bundles 里有没有它；②patch 里有没有被 `disabled: true` 或配错；③`%APPDATA%\@deepseek-ai\dsh-desktop\plugin-operations\operations.jsonl` 有无安装/启用记录；④会话日志里有无该组件的请求事件与参数；⑤UI 有没有反馈（这类后台组件**完全没有**，所以「没变化」不等于「没运行」）。
