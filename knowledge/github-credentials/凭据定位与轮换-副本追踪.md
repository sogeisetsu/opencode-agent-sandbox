# 一把凭据存在几处：怎么只读地查出来

## 一份 token 通常不止一份

> 草图：[`凭据副本树.excalidraw`](./凭据副本树.excalidraw)（OpenChamber 的 Files 视图里点开就是画布）

一份"权威副本"被读取后，常被顺手写到别处：CLI 自带凭据库、系统凭据管理器、会话数据库、命令输出落盘文件、备份 / WAL。

- **系统凭据管理器**：条目名通常形如 `<工具>:<主机>`（如 `git:https://<host>`），不是普通文件。
- **会话数据库**：AI 助手 / 聊天工具的 SQLite；你在对话里打印过 token，它就会落进去。
- **命令输出落盘**：命令输出被持久化成文件时，输出里的 token 也跟着落盘。
- **备份 / WAL**：SQLite 的 `-wal`、`.bak`、编辑器备份，都是常见漏网处。

**关键认知**：你以为只有一处，实际可能有五六处；而且系统里常同时存在**好几把不同的 token**（不同工具各自登录一次），长得像但不是同一把。

## 怎么判断"是不是同一把"（全程不打印明文）

原则：**只比较长度 + 哈希前缀**，永远不把明文写进终端、文件或回复。

- 从配置文件里按 key 名提取敏感叶子（`*token* / *secret* / *password* / *authorization*` 等路径），打印 `len` + `sha256[:10]` + 前 4 字符。
- 用同一个值去扫目录/数据库，统计命中位置。
- SQLite 里要定位到"哪张表哪一列"，才能区分**设计如此**（凭据表）和**副作用**（会话/日志表）。

`secrets-scan` skill 就是把这三步脚本化了（`extract` / `scan` / `dbtables`，带 `selftest`）。只想手搓时也照这个思路做。

## 容易漏的几处

| 位置 | 说明 |
|---|---|
| CLI 自己的凭据库 | 可能是系统凭据管理器条目（形如 `git:https://github.com`、`工具名:主机名`），不是文件 |
| 命令行工具的配置文件 | 有的把 token 明文写进 `*.yml` / `*.json` |
| 会话/消息数据库 | AI 助手、聊天工具的 SQLite；**你在对话里打印过 token 就会落进去** |
| shell 输出落盘 | 命令输出被持久化成文件时，输出里的 token 也跟着落盘 |
| `*-wal` / 备份 | SQLite 的 WAL、`.bak`、编辑器备份 |

## 轮换顺序（重要）

1. 先在权威处**吊销 + 重新授权**（旧值立刻失效）；
2. 再处理扩散副本：**活着的副本**要更新，**历史副本**（会话/日志）留着也已是废票，想干净就删记录；
3. 轮换后确认其他工具没被带崩：**同名不同值的 token 是各自独立的**，吊销一个不影响另一个。

## 反面教材（本沙箱真实发生过）

为了"查配置"，直接整文件读出来 + 掩码正则写错（`"[^"]*"\s*:` 这种只匹配 key 的写法在替换后**保留了值**），结果把明文打进了会话，并被持久化进数据库和 shell 输出文件。

教训：**掩码要在"提取后"做，不要赌正则**；能只输出 `len + sha256[:10]` 就别输出值。
