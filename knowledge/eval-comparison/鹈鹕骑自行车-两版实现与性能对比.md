# 两个"鹈鹕骑自行车"动画：实现效果与性能对比

## 对比对象

| 产物 | 模型 | 相对路径 |
|---|---|---|
| DeepSeek 版 | DeepSeek V4.1 flash 1017 | [`../../evals/pelican-bike/deepseek-v4.1-flash-1017.html`](../../evals/pelican-bike/deepseek-v4.1-flash-1017.html) |
| MiniMax 版 | MiniMax M3.1 Flash Free | [`../../evals/pelican-bike/minimax-m3.1-flash-free.html`](../../evals/pelican-bike/minimax-m3.1-flash-free.html) |

**前提（未验证）**：两次是否用了完全相同的提示词，**无法确认** —— 按 `evals/README.md` 的记录，提示词原文未存档；MiniMax 那版是在一次对话里直接产出的，DeepSeek 那版来自 multi-run。下面所有结论都是**在"同一任务"前提下**对成品动画本身的比较，与提示词无关。

## 一句话结论

**性能打平，动画实现 DeepSeek 版更对。** 两份的主线程开销都在每帧 2ms 以内（预算 16.7ms），差距全在"动得对不对"：DeepSeek 版的脚精确踩在踏板上，MiniMax 版的脚掌图形画在了膝盖上。

## 一、结论总表（已验证）

| 维度 | DeepSeek V4.1 flash | MiniMax M3.1 Flash |
|---|---|---|
| 脚是否踩在踏板上 | **是**，实测偏差 0px | **否**，脚掌图形离踏板 46px（画在膝盖上） |
| 脚掌是否保持水平 | 是（额外反向旋转） | 否（随小腿一起转） |
| 两条腿膝盖朝向 | 同向朝前（向后折占比 0） | **反向**（近侧 100% 向后、远侧 100% 向前） |
| 曲柄 / 车轮齿轮比 | **1.855**（应≈1，错） | **1.000**（对） |
| 地面滚动速度 / 轮面速度 | **0.354**（轮子像原地空转） | **1.000**（对） |
| 背景层次 | 只有云在动，山和灌木全静止 | **六层视差**（远山 0.14 → 路面 1.0） |
| 次级动作 | 速度线、尘土、阳光射线、拍翅、嗉囊 | 围巾、尾羽、眨眼、冠羽、身体起伏与侧倾、飞鸟、草丛 |
| 自行车本体 | 真车架 + 虚线链条 + 牙盘飞轮 | 车架可用，链条是两条平行直灰线 |
| 主线程每帧总耗时 | 1.83 ms | 1.72 ms |
| 每帧 DOM 属性写 | 10 次 | 15 次 |
| 长任务 / 掉帧 | 0 | 0 |

**综合判断**：如果只看"一眼看上去动得对不对"，DeepSeek 赢（脚和膝盖是整个动画的焦点，MiniMax 那处 bug 每帧都看得见）。如果只看"场景与运动丰富度"，MiniMax 赢。**把 MiniMax 的 46px 偏移修掉之后，MiniMax 全面领先**（它的传动系物理和视差层次本来就更对）。

## 二、MiniMax 版的关键 bug（已验证）

### 1. 脚掌画在膝盖上，不在踏板上

```html
<g id="shinF">
  <path d="M0,0 L0,46" .../>                    <!-- 小腿：从 0 走到 46 -->
  <path d="M-8,-4 L8,-4 L15,10 L-15,10 Z" .../> <!-- 脚掌：没有任何位移 -->
</g>
```

`shin` 组被放在膝盖处（`translate(0 52) rotate(...)`），脚掌路径没有偏移量，于是落在 shin 组原点 = **膝盖**。小腿末端（小腿路径的终点）确实是精确落在踏板上的，但那里只有一个光秃秃的圆头线段。

实测（浏览器活体 DOM，见第四节方法）：

```
nearLeg: shinEnd_shouldBePedal=[474.6,362.8]  footGraphicAnchor=[454.5,321.4]  gapPx=46
farLeg : shinEnd_shouldBePedal=[449.4,317.2]  footGraphicAnchor=[485.7,288.9]  gapPx=46
```

46px 正好等于小腿长度 L2 —— 即脚掌整体错位了一整条小腿。**修法**：给脚掌路径加上 `translate(0 46)`，或把它挪到 `translate(0 46)` 的子组里。

### 2. 两条腿膝盖反向

`setLeg(thighF, shinF, HIPF, theta, 1, bob)` 用 `bend=+1`、`setLeg(thighB, shinB, HIPB, theta+Math.PI, -1, bob)` 用 `bend=-1`，两腿的膝关节朝相反方向弯。骑行时膝盖应同向（朝前进方向）。实测 360 个采样点：近侧腿 100% 向后折，远侧腿 100% 向前折。

### 3. 踏板跟着曲柄一起转

`crank` 整个组 `rotate(deg 462 340)`，两个踏板矩形是组内子元素，所以踏板跟着转。真实自行车的踏板应保持水平。DeepSeek 版用 `rotate(-d2)` 反向抵消了这一点。

### 4. 灌木层每 2.17 秒整层横跳 300px

灌木的 x 坐标是 `30,150,268,410,545,690,820`（间距 120/118/142/135/145/130，不均匀），但回绕步长是 `-(v*0.55*t) % 300`，300 与这些间距不整除 —— 每次回绕整个灌木层会瞬移 300px，前景草皮上会"啪"地跳一下（回绕周期 300 ÷ 138.2 ≈ 2.17s）。云层同样不无缝，但 900px 步长 vs 不均匀间距，回绕周期 71.6s，碰见的次数少。

### 5. 废代码

`<filter id="soft">`（`feGaussianBlur`）定义了但全文没有任何引用。

## 三、DeepSeek 版的问题（已验证）

### 传动系不对，车轮像在原地空转

- 曲柄一圈 1.15s（JS `PERIOD`）→ 0.87 圈/秒
- 车轮辐条一圈 0.62s（SMIL `animateTransform dur="0.62s"`）→ 1.61 圈/秒
- **齿轮比 1.855**（真实自行车曲柄与后轮是 1:1 或固定齿比）
- 车轮表面线速度 2π×72÷0.62 = **729.7 px/s**，而路面虚线滚动 160÷0.62 = **258.1 px/s**
- **地面只跑轮面速度的 35.4%** → 轮子转得飞快、路却走得很慢

代价就是：脚踩得很慢、轮子转得很快、两者的节奏对不上。

### 背景没有纵深

山和灌木是静止的，只有云和路面在动。速度线（3 条）和尘土粒子（2 个）倒是加得不错。

### 好的地方

- 脚踝与曲柄端点实测偏差 **0px**（`ankle_vs_crankEnd_gap: 0`）
- 脚掌组额外 `rotate(-d2)`，叠加后净旋转为 0 → 脚掌始终水平
- 膝盖始终朝前进方向折（向后折占比 0）
- 膝盖弯曲范围 14°~98°，行程幅度比 MiniMax 大得多，看起来是真的在蹬
- 云层 `x` 间距正好 300、回绕步长也 300 → 无缝；路面虚线间距 160、回绕 160 → 无缝

## 四、性能：两边打平（已验证）

同一台机器、同一个 headless Chrome、同一个窗口测出来的：

| 指标 | DeepSeek | MiniMax |
|---|---|---|
| 主线程每帧总耗时 | 1.83 ms | 1.72 ms |
| └ rAF 回调 | 0.51 ms | 0.42 ms |
| └ Paint（2 次/帧） | 0.40 ms | 0.46 ms |
| └ UpdateLayoutTree | 0.39 ms / 4.3 次 | 0.36 ms / 2.6 次 |
| └ Layout | 0.19 ms | 0.16 ms |
| └ PrePaint | 0.15 ms | 0.16 ms |
| └ RasterTask（合成线程） | 0.20 ms | 0.21 ms |
| 每帧 DOM 属性写 | 10 | 15 |
| DOM 节点数 | 164 | 220 |
| 长任务 | 0 | 0 |

两边都远低于 16.7ms 预算（约 10 倍余量），**性能上分不出高下**。唯一差别在写法：DeepSeek 把背景滚动交给 SMIL 声明式动画（不写 DOM，每帧 10 次属性写，但样式重算次数多）；MiniMax 靠 rAF 手写 transform（每帧 15 次属性写，样式重算次数少）。

## 五、怎么复现这些结论（已验证）

### 1. 运动学：把 IK 公式复刻到 node 里跑 360 个采样点

读源码取出常量（髋点、中轴、曲柄半径、两段腿长、周期），复刻两骨 IK：

```js
// 由髋和脚反解膝盖
const cosA = (L1*L1 + d*d - L2*L2) / (2*L1*d);
const a    = Math.acos(clamp(cosA, -1, 1));
const ang  = Math.atan2(dy, dx) + bend * a;
const knee = { x: hip.x + L1*Math.cos(ang), y: hip.y + L1*Math.sin(ang) };
```

然后逐项算：脚掌图形与踏板的距离（**注意元素局部坐标 ≠ 父级坐标**，脚掌路径没写偏移就落在 shin 原点）、膝盖朝向（叉积，SVG 的 y 向下所以符号与直觉相反）、齿轮比、地面速度与轮面速度之比。

### 2. 活体 DOM：量元素到底在哪

```js
function toVB(el, x, y) {                    // 元素局部坐标 -> viewBox 坐标
  const p = svg.createSVGPoint(); p.x = x; p.y = y;
  const s = p.matrixTransform(el.getScreenCTM());
  return s.matrixTransform(svg.getScreenCTM().inverse());
}
```

- `toVB(shin, 0, 46)` = 小腿末端（应为踏板）
- `toVB(footPath, 0, 0)` = 脚掌图形锚点
- DeepSeek：`toVB(footGroup, 0, 0)` 与曲柄线段端点 `x2/y2` 对比 → 偏差 0

### 3. 性能：CDP trace

用 `performance_start_trace` → 跑 4 秒 → `performance_stop_trace` 落盘 `trace.json.gz`，用 node 解压聚合。**测量窗口要用 `FireAnimationFrame` 事件的首尾**（rAF 回调），不能用整份 trace 的 min/max ts（会混进无关进程，跨度离谱）。详见 [`../chrome-devtools-mcp/动画性能-用trace量每帧开销.md`](../chrome-devtools-mcp/动画性能-用trace量每帧开销.md)。

### 4. 前置注意

- **页面必须在前台**：后台标签页的 rAF 被 Chrome 节流到 1Hz，测出来的帧率完全失真。
- 开页面用 `new_page({ background: true })` 避免抢前台，详见 [`../chrome-devtools-mcp/抢前台-后台开页面与rAF节流.md`](../chrome-devtools-mcp/抢前台-后台开页面与rAF节流.md)。

## 六、给后续评测的提醒

1. **动画类产物不能只看截图** —— 脚画在膝盖上这种 bug，缩略图里几乎看不出来，必须量坐标。
2. **自洽性检查比"参数多不多"重要**：曲柄周期、车轮周期、地面滚动速度这三个数必须对得上，否则一眼假。
3. **深度排版元素要检查回绕无缝性**：间距必须与回绕步长整除，否则会周期性瞬移。
4. **两个模型的产出不要互相"修好"** —— 本文件只做对比与取证，原始产物保持原样（见仓库根 `AGENTS.md` 的 evals 约定）。
