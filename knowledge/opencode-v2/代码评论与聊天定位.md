# Desktop 的代码评论能力，与"OpenCode 没有聊天"这个误解

> 核对范围：上游 `anomalyco/opencode` 的 `dev` 分支（2026-11-05 取文件），**源码已验证**。
> 界面快捷键与"某页签会失败"这类现象**未在运行时复现**，标 **推测/未核实**。
> 三端架构见 `一个服务撑三端.md`；审查命令归属见 `review-commands/`。

## 一句话

代码评论是**真实存在**的能力，落点是 composer（输入框）——评论最终作为 prompt 附件发给模型；而"OpenCode 没有聊天"是误读：它以 **session** 为聊天单位，只是 session 与项目/工作目录绑定。

## 1. 代码评论在源码里的位置

证据：`packages/app/src/composer/comment-note.ts`（130 行）。关键结构：

```ts
const PromptFileComment = Persistence.struct({
  type: Schema.optional(Schema.Literal("file")),
  path: Schema.String,
  selection: Persistence.optional(FileSelection),   // 行/列选区
  comment: Schema.String,
  preview: Persistence.optional(Schema.String),
  origin: Persistence.optional(Schema.Literals(["review", "file"])),
})
```

可确认的四点（**已验证**）：

1. 评论带 `path` 与 `selection`，所以能定位到**具体文件的具体行段**，不是笼统的"这条评论挂在这个会话上"。
2. `origin` 区分 `review`（审查场景）与 `file`（看文件时随手评论）两条来源。
3. 评论被打包进 **prompt 的展示层**（`displayText` + `comments` + `attachments`），随下一条消息发给模型。
4. 存在 `durableNote` / `LegacyBrowserNote` / `NoteComment` / `QuoteComment` 多种 note 形态，说明评论不只一种入口。

推论：评论不是"给未来自己看的便签"，而是**给模型的输入**。所以评论写清楚"为什么错、期望什么"比写"这里有问题"有用得多。

## 2. 界面操作（未核实）

对话里流传的说法是：在 **Changes** 标签页选中代码 → 按 `c` → 输入评论 → `Ctrl+S` 保存；评论会自动附加到 Agent 输入框；在 **All files** 标签页添加评论可能失败。

- 源码只证明"评论会进 composer"，**没有证明快捷键是 `c`**。键位可能随版本变，也可能被用户配置覆盖。
- "All files 页签失败"属**已知问题传闻**，未复现。遇到时先确认：是否已打开 diff 视图、选区是否跨文件、版本是否最新。

## 3. 为什么说"OpenCode 不是没有聊天"

- OpenCode 的原生单位是 **session**：每个 session 有自己的上下文、历史、工作目录。UI 上看到的是一个会话列表，而不是"聊天频道 + 项目"两套东西。
- 因此"聊天"和"编码任务"共用同一个容器：你在 session 里说的话、贴的代码、挂的评论，都进入同一条上下文。
- 想要**脱离项目**的纯聊天，才需要外部方案（OpenChamber 的 Chats 等）。**未核实**：OpenChamber 当前版本是否把 Chats 与项目彻底解耦，以及它读的是哪份存储。

判断标准很简单：**这条对话要不要读你的仓库？** 要 → 用 session；不要 → 用独立聊天工具，别硬塞进项目会话（会污染上下文、也会让模型误以为你要改代码）。

## 4. 评论、审查、交接三者的关系

| 动作 | 产出 | 落点 |
|---|---|---|
| 代码评论 | 一条带路径与选区的 note | 下一条发给模型的 prompt |
| `/review` / `/workspace-review` | 一份审查报告 | 当前或子会话的消息 |
| `/handoff-review` | 交接摘要 + 新会话 | 另一个 agent 会话 |

所以"评论"是**粒度高、即时**的输入；"审查"是**成体系、只读**的输出；"交接"是**跨会话**的流程。三者互补，不能互相替代：拿评论当审查会漏掉全局问题，拿审查代替评论会让模型不知道你具体在意哪一行。

## 5. 轻量前端能不能替

`OpenCodeUI`（576★）这类"纯 UI"项目读的是同一份本地会话数据，能提供 Chat、Diff、文件查看，但通常没有多 agent 编排与审批面板。取舍见 `agent-harness-and-clients/开源桌面Harness与轻量客户端.md`。

## 6. 怎么复核（只读）

```bash
gh api repos/<owner>/<repo>/contents/packages/app/src/composer/comment-note.ts -H "Accept: application/vnd.github.raw"
gh api "search/code?q=repo:<owner>/<repo>+comment+path:packages/app/src&per_page=10" --jq '.items[].path'
```

搜 `comment` 时别只搜 `packages/desktop`——GUI 能力在 `packages/app`（见 `源码对照与旧结论纠错.md` 的教训：在一个包里搜不到，不等于功能不存在）。
