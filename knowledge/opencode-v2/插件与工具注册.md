# V2 插件与工具注册：API 形状与几个容易传错的点

> 核对范围（**已验证**）：上游 `anomalyco/opencode` 的 `dev` 分支，commit `c24760c`（2026-10-29）；运行时装机版本 `opencode v2.1.4`（Windows）。除源码外，另用一个临时项目实跑：插件文件被加载、工具出现在注册表里、改名规则生效、单文件配置被拒、辅助文件被当成插件而报错。文中 `已验证` 指这两条证据至少有一条，`推测` 指只有推理。

## 一句话

V2 里**用户自定义工具只能由插件注册**，没有 V1 那种 `.opencode/tools/*.ts` 工具文件形态；注册入口是插件 `setup(ctx)` 里的 `ctx.tool.transform`，参数 schema 也不是只能写 JSON Schema。

## 1. 没有独立的“工具文件”

- V2 只扫描 `{plugin,plugins}` 两个目录（`packages/core/src/plugin/source-directory.ts`），不扫描 `.opencode/tool/` 或 `.opencode/tools/`。
- 实跑时在 `.opencode/tools/legacy.ts` 放了一个文件，日志里**没有**任何 `loading plugin` 记录，注册表里也没有对应工具。
- 因此 `.opencode/tools/` 里放 V1 的 `tool()` 文件，在 V2 下不会生效；它只是普通文件。

## 2. 最小注册写法

```ts
import { Plugin } from "@opencode/plugin"
import { Schema } from "effect"

export default Plugin.define({
  id: "example",
  setup: async (ctx) => {
    await ctx.tool.transform((editor) => {
      editor.add({
        name: "echo",
        description: "Echo text",
        input: Schema.Struct({ text: Schema.String }),
        execute: async ({ text }, context) => {
          context.progress({ message: "echoing" })
          return { output: { text }, content: text }
        },
      })
    })
  },
})
```

要点：

- `transform` 的回调是**同步**的；要异步取数据，先 `await` 取完再注册（官方 Promise API README 明确写了）。
- `await ctx.tool.transform(...)` 返回 `Promise<Registration>`；`Registration.dispose()` 会撤掉**这个 transform**，并让被它覆盖的早期定义重新生效。
- `editor.add/update/remove/namespace` 本身返回 `void`，不返回 `Registration`。
- 插件默认导出必须是 `{ id, setup }` 或 `{ id, effect }`；运行时校验失败会报 `Plugin must export a default definition with an id and an effect or setup function`（实测）。

## 3. API 形状（比流传汇总更容易写错的地方）

`Tool.Info`（`packages/schema/src/tool.ts`）：

| 字段 | 说明 |
|---|---|
| `name` | 工具名；非法字符会被替换成 `_` |
| `description` | 给模型看的说明 |
| `input` | **Effect Schema、Standard Schema 或原生 JSON Schema 三者之一** |
| `output` | 可选，用于声明结构化输出 |
| `execute(input, context)` | Promise API 里返回 `Promise<Tool.Result>` |
| `options` | `namespace`、`permission`、`codemode`、`pinned` |

`ToolContext`（Promise API）：`sessionID`、`agent`、`messageID`、`id`、`signal`、`progress`。`progress` 是 `Promise<void>`；`signal` 要自己传给可取消操作。

`ToolDomain`：

- `transform(callback)` → `Promise<Registration>`
- `list()` → `Promise<readonly (Info & { id })[]>`
- `reload()` → `Promise<void>`
- `hook("execute.before" | "execute.after", cb)` → `Promise<Registration>`

`ToolEditor`：

- `list()` / `get(id)`
- `namespace({ name, description })`
- `add(tool)` / `update(id, fn)` / `remove(id)`

`update`/`remove` 按**最终生效名**匹配；缺失时静默忽略。`update` 会保留原来的 name 和 namespace，改坏了保持旧定义。

## 4. 命名、CodeMode、权限

- 最终名：没有 namespace 时等于 `name`；有 namespace 时是 `<namespace>_<name>`。
- 工具名里的非 `[A-Za-z0-9_-]` 字符替换为 `_`；namespace 里的点号在拼接时也变成 `_`。实跑注册 `probe.echo`，注册表里出现的是 `probe_echo`（已验证）。
- namespace 每段仍要匹配 `[A-Za-z0-9_-]+`，否则注册失败；已经注册过的 namespace 才有描述，未注册只是没有描述，不影响使用。
- `codemode` **默认 true**：工具默认进 CodeMode 的 `tools.<namespace>.<tool>` 调用面；`codemode: false` 才留在 provider 的原生工具列表。`codemode: false` 时名字 `execute` 被保留，不能占用。
- `options.permission` 只影响**工具定义是否出现在目录里**，不做执行授权。工具注册表本身没有 `Permission.Service`；插件工具要在 `execute` 里自己调 `ctx.permission.assert(...)`（或自行做检查）。内置工具是在各自的 leaf 里做权限判断的。

## 5. 发现与配置

- 项目级：`.opencode/plugin/` 和 `.opencode/plugins/` 都扫。
- 全局级：`~/.config/opencode/plugin/` 和 `~/.config/opencode/plugins/` 都扫。
- 每个 `.ts` / `.js` 文件、以及**每个子目录**都会被当作插件目标；目录需要能解析到 server/GUI/TUI 入口。
- 配置 `plugins: [...]` 支持 npm/Git 包和本地路径；本地路径**必须是目录**，指向单文件会打 `configured plugin path must be a directory` 并跳过（实测）。相对路径从该配置文件所在目录解析；对象形式可带 `options`。
- 旧键 `plugin` 仍会被规范化成 `plugins`（源码 `config/normalize.ts`）。
- `opencode plugin add` 把 npm/Git 包装进**全局**配置；`remove`/`update` 也只针对全局配置里的包插件。`list` 会同时列本地插件，不只列包。

## 6. 为什么运行时实现常被收在单文件

宿主对插件目录里**每个顶层 `.js`/`.ts` 文件和每个子目录**都发起加载。把辅助模块拆成同目录的 `helper.ts`，它会被当成一个独立插件，因缺少默认导出而加载失败——实测报错就是上面那句 `Plugin must export a default definition...`。所以除非把辅助代码放进一个带入口的独立子包，运行时实现通常收在一个文件里最省事。安装脚本、文档、CI 不在加载路径内，可以多文件。

## 7. 与 V1 的差异

- V1 的 `tool()` 辅助函数不在 V2 的 `@opencode/plugin` 包里；V2 用 `ctx.tool.transform` + 完整的工具对象。
- V1 插件实现（命名导出、返回 hooks 对象）在 V2 不运行：V2 要求默认导出 `{ id, setup }` 或 `{ id, effect }`。实测一个只有命名导出的文件直接加载失败。
- 参数 schema：V1 的 `tool({ args: z.object(...) })` 写法不再适用；V2 接受 Effect Schema、Standard Schema（Zod 4 属于这一类，源码里对 `$ZodType` 走 `toJSONSchema`）或原生 JSON Schema。
- `execute` 签名是 `execute(input, context)`，工具名显式写在 `add({ name })`，不再靠文件名。

## 8. 设计层判断（非源码结论）

很多能力（读 skill/agent 注册表、按调用者 agent 求值、`ctx.agent.reload()`、回读全局配置）只有插件上下文拿得到；纯工具执行器通常只有入参和一份调用上下文。因此“需要插件上下文”是很多工具被做成插件的设计层原因，平台限制只是其中一层。这条是**推测/判断**，不是源码里写死的规则。
